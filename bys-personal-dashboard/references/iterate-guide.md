# 迭代指南

用户已经有工作台了，来改东西。**不要重新走初始化流程。**

## 怎么判断是迭代

目录里有 `工作台配置.md` → 迭代。

或者用户说的话像这些：
- 「给我的工作台加个喝水提醒」
- 「工作台换个配色」
- 「把记账那个删掉」
- 「单词背完了，再生成一批」
- 「工作台在手机上有点挤」

## 标准动作

1. **读 `工作台配置.md`** —— 功能清单、风格参数、数据结构、部署状态都在里面
2. **读 `index.html` 里相关的分区** —— 用 Grep 找 `==== 功能：XXX` 定位，不要整file读
3. 改
4. 跑验收脚本
5. **更新 `工作台配置.md`**（功能表 + 变更记录 + 行数）
6. 已部署的话，提醒用户重新上传

第 5 步最容易忘。配置文件和实际工程不同步，下一次迭代就会出错。

## 常见迭代类型

### 加功能

1. 判断类型（本地/内容/联网），联网型照例先说门槛
2. 在 `index.html` 加一段带分区标记的 HTML 和 JS
3. 在 `App.routes` 加一条
4. **检查侧边栏是不是挤了**——超过 9 个在手机上会滚动，建议用户合并或删掉不用的
5. 更新配置文件

不用重新出风格预览，直接沿用配置里的 CSS 变量。

### 删功能

1. 删 HTML 分区、JS 分区、routes 那一条，三处都要删
2. **问用户旧数据要不要留**：
   > 记账的历史数据要保留吗？留着的话以后想恢复这个功能，数据还在；不留我就一并清掉。
3. 留就什么都不做（Store 里的数据不影响），不留就在删除时清掉对应 key
4. 更新配置文件

### 换配色

1. 只改 `:root` 里那一段 CSS 变量，以及 `manifest.json` 的 `theme_color`/`background_color`
2. 变量都改对了的话，整个界面会一起变——这就是当初集中定义的好处
3. 换了主色建议一并重做图标（`build-guide.md` 图标章节）
4. 提醒：**换图标后要删掉桌面上的旧图标重新添加**，iOS 会缓存

### 内容型功能续期

用户说「单词背完了」：
1. 生成新一批内容
2. 替换 `CONTENT` 数组，把 `START` 改成今天
3. 更新配置文件里的到期日
4. 顺便问一句难度要不要调整——用户背了 60 天，水平可能变了

### 改布局 / 嫌挤

手机上挤，通常是这几个原因，按顺序查：
- 侧边栏功能太多（>9 个）→ 合并或删
- 卡片 padding 太小 → 加大，不是缩小字号
- 一页塞了太多卡片 → 拆成两个功能，或者把次要卡片折叠

**不要靠缩小字号解决拥挤**，那是治标。

## 迭代时的红线

- 不要改 `Store` 的命名空间（`bysdash:`）——用户已有的数据会全部读不出来
- 不要改已有功能的 Store key 名——同上。真要改必须写数据迁移
- 不要把 `Util.esc()` 去掉
- 不要在迭代时"顺手优化"用户没让你改的地方——他会以为工作台坏了
- 改完必须跑验收脚本

## 用户抱怨"不好用"时

先问清楚是哪一种，别急着改代码：

| 用户说 | 通常真正的问题 |
|---|---|
| 「用了几天就不想打开了」 | 打开后没有"今天该干什么"的即时反馈。加一个今日概览卡，或把最常用的功能设为默认首页 |
| 「记不住要打卡」 | 网页做不到推送提醒。建议用手机自带的闹钟/提醒事项配合 |
| 「数据没了」 | 先查是不是换了浏览器/设备打开的（数据跟设备走，不跟链接走）。确实丢了就用备份恢复 |
| 「加载慢」 | 查是不是引了外部 CDN 或者塞了大图。国内访问外部 CDN 会很慢 |
| 「手机上打不开」 | 十有八九是在微信里点的链接。引导「用其他应用打开」 |
